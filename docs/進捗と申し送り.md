## 1. これは何か

腕時計の価格比較サイト。楽天市場・Yahoo!ショッピングの出品価格を毎日自動収集し、
型番ごとに最安値を並べる。全自動で運用し、アフィリエイトと買取リードで収益を得る。

- 公開URL: https://watch-price-navi.github.io/watch-price-navi/
- リポジトリ: https://github.com/watch-price-navi/watch-price-navi （**Public**。秘密情報を絶対に置かない）
- 掲載: 39ブランド / 29,269モデル（人手968 + 自動28,301）
- 構成: Next.js 15 App Router / `output: 'export'` の静的書き出し / GitHub Pages

## 2. 自動運用（触らなくても毎日動く）

GitHub Actions の2本が毎日動く（2026-08-17の改装で Instagram 投稿を別ワークフローに分けた）。

| 時刻(JST) | ワークフロー | 内容 |
|---|---|---|
| **6:20** | update-prices.yml | 記事1本生成 → 投稿画像作成（3枠＋ストーリー）→ 価格収集 → 新作検出 → サイト公開 |
| **11:05** | instagram.yml | Instagram 朝の投稿（その日の記事のカルーセル）＋ストーリー |
| **18:05** | instagram.yml | Instagram 昼の投稿（ブランドの物語） |
| **18:20** | update-prices.yml | 価格収集 → サイト公開（記事生成はしない） |
| **21:05** | instagram.yml | Instagram 夜の投稿（時計用語の解説）＋ストーリー |

朝の回の所要は2〜3時間。**毎時0分はGitHub側が混雑して最大50分遅れる**ためずらしてある。
投稿を6:20の回に入れないのは、画像が公開されるまで投稿できない（404で必ず失敗する）ため。
トークンの延長・書き戻しも投稿と一緒に instagram.yml が行う（分けると延長されなくなる）。

なお**観測事実（2026-08-19に確認・仕組みは未確認）**: 深夜0時すぎに watch-bot が
「post: 翌日の記事を追加 [skip ci]」（記事＋投稿データ＋page-stats.json）を押してくる。
公開リポジトリのワークフローの実行記録には無いので、**非公開の収益リポジトリ側の
ワークフローが GH_PAT で押している**と見られる（Search Console 連携で作った仕組み）。
このため 6:20 の回の記事生成ステップは、既に記事がある日は何もしていないはず。
収益リポジトリを触るときは、この深夜の書き込みを壊さないこと。

### 設計上、絶対に壊してはいけない約束

- `concurrency.cancel-in-progress: false` … 進行中の実行を止めない。
  以前 true にしていて、価格収集の最中にpushして収集ごと打ち切る事故を3回起こした。
- **価格データが無いビルドは公開しない**（`Check price data before deploying`）。
  push実行は収集を飛ばすので、そのまま公開すると中身の無いサイトが良い版を上書きする。
- 夕方の回を判定する `github.event.schedule != '20 9 * * *'` が**8箇所**ある。
  cronを変えるときは全部揃えること。揃え忘れると夕方にも記事生成とInstagram投稿が走る。

## 3. 収益の構造（配置を考えるときの前提）

| 経路 | 1件あたり | 状態 |
|---|---|---|
| **買取リード（みんなの買取）** | **7,500〜10,000円** | 稼働中 |
| eBay (EPN) | 4%・上限$550 | 稼働中 |
| 楽天 | 2%・**1商品1,000円上限** | 稼働中 |
| Yahoo! (バリューコマース) | 約1% | 稼働中 |
| 米田屋（もしも） | 要確認 | 稼働中 |
| AdSense | 微額 | 稼働中 |

**買取が楽天の約10倍**。しかも購入という重い決断が要らずフォーム入力だけで成立する。
だから買取導線を最優先で配置している（ヘッダー「時計を売る」／`/sell/`／出品の無いページでは最上部）。

eBayは単価が大きいが**成果の有効期間が24時間**しかなく、最終クリック方式。
契約は**0日前通知で変更・解除できる**ので、収益の柱にしてはいけない。

## 4. 規約の制約（これを破るとサイトが死ぬ）

### 楽天ウェブサービス規約 第8条4項 ← 最重要

> ウェブサービスを使用した部分において、楽天のサイト以外へのリンクを設けてはならない

**楽天から取得した写真・価格を表示している領域からは、楽天以外へリンクできない。**
違反すればAPI利用停止＝価格も写真も取れなくなり、サイトの中身が全部消える。

## 7. これからやること

### 【解決済み 2026-08-19】Instagram が3日間停止した（Metaチェックポイント起因）

停止期間は 8/16 12:11 〜 8/19 14:14 JST（定期投稿8回ぶん）。8/19 14:14 に実投稿で復旧を確認。
サイト本体・価格収集には終始影響なし。

**本当の原因**: Facebookアカウントが「チェックポイント」（本人確認の関所）に入り、
**その時点で発行済みのIGAAトークンが恒久的に無効化された**。
スマホのFacebookアプリで本人確認を通してアカウントを復旧させても古いトークンは死んだままで、
ダッシュボードから新しいトークンを発行し、Secrets の `IG_ACCESS_TOKEN` を差し替えて解決した。
途中で立てた「未公開アプリが弾かれ始めた」「アプリごと凍っている」という仮説は**どちらも外れ**
（アプリは無罪。ダッシュボードに警告なし・アラート受信箱も空だった）。

次に `400 API access blocked. (code 200)` を見たときの手順:
1. **トークン切れの code 190 とは別のエラーだが、トークンの死をまず疑うこと。**
   トークンの持ち主のアカウントがチェックポイントに入ると、このエラーになる。
2. 見分け方: Metaダッシュボード → ユースケース「Instagramでメッセージとコンテンツを管理」→
   **「トークンを生成」で新しいトークンを発行し、curl で `/me` を叩く**。
   新トークンが通れば古い鍵の死（差し替えて終わり）。新トークンも弾かれたらアプリ側の問題。
3. チェックポイント画面がPCで「エラーが発生しました（現在修正作業中です）」と壊れていても、
   **スマホのFacebookアプリからなら通れる**（実績あり）。
4. GitHub の Secrets 画面（運営リンク集にリンクあり）が **404 になるのは
   `watch-price-navi` アカウントでログインしていないとき**。権限が無いと404が返る仕様。
5. 復旧確認は Actions の「Instagram check」を「実際に投稿する」で実行（1分）。

### ストーリーにタップできるリンクは付けられない（Metaの仕様・2026-08-19確認）

APIで投稿するストーリーには**リンクスタンプを付けられない**。手動でアプリから
投稿する場合のみ可能（Buffer等の大手ツールも同じ理由で非対応）。
次善として、ストーリー下部に「記事と最安値は、プロフィールのリンクから」の誘導文と
リンク風の錠剤型のURL表示を入れた（`build-instagram-extra.mjs` の `chip`）。
特に届けたい日だけ、アプリから手動で同じ画像を投稿してリンクスタンプを貼る手はある。
なお画像内に絵文字は使えない（CIのlibrsvgに絵文字フォントが無く豆腐になる）。

### 朝の表紙を「時計の実写」優先に変更（2026-08-19）

復旧初日の投稿の表紙がジュネーブの街並みになり、「時計の写真にできないか」と指摘を受けた。
昼・ストーリーは時計の写真プールを使うのに、**朝の表紙(`build-instagram-post.mjs` の
`pickBackground`)だけが発祥地→創業者の順でしか探していなかった**（8/17の改修の入れ忘れ）。

新しい優先順: ①記事のモデルの実写 → ②同ブランドの別モデルの実写 → ③発祥地→創業者→スタイリング。
②を使うときは「（同ブランドの別モデル）」を**画像の隅と本文の両方**に必ず出す
（読者が記事の時計の写真だと誤解したまま買いに行くのを防ぐ）。ストーリーも同じ断り書きを付けた。
作者名が台帳に無い写真は、本文に出典ページのURLを載せて表示義務を果たす。

写真プールの在庫は46ブランド（各1〜6枚）。`data/watch-photos.json` が台帳で、
毎朝 `fetch-watch-photos.mjs` が増やしていく。**モデル別の写真は33モデルにしか無い**ので、
表紙はしばらく②（同ブランド別モデル）が主になる。eBay承認が下りれば①が本命になる。

あわせてレビューで見つけた出典まわりの穴を塞いだ（同日）:
- 台帳の `provider` は Openverse 経由だと供給元スラッグ（flickr 等）が入る。
  `=== 'openverse'` の判定は決して成立せず、Flickr の写真に「via Wikimedia Commons」と
  出るところだった。source のURLも見て判定する。
- 写真もゆかりの画像も無いブランド（16社ある）の記事の日、ストーリーが**他ブランドの
  時計**を断り書き無しで背景にしていた。断り書きでは足りないので、世界観画像に落とす。
- 作者名の無いCC BY写真（プール184枚中17枚）が昼・夜でライセンス名だけになっていた。
  作者が無いときは出典サイト名＋出典URLを本文に必ず出す。夜の本文には出典行自体が無かったので足した。

2026-08-18 に直したもの（復旧後に正しく動くための修正。どちらも有効）:
- ストーリー投稿に `media_type=STORIES` が無く、**通常のフィード投稿として出てしまう**
  バグを修正（エラーにならないので出てから気づくところだった）。
- トークン延長の書き戻しが update-prices.yml に置き去りで、投稿だけが instagram.yml に
  移っていたため**誰もトークンを延長しない**状態だった。延長・書き戻しを instagram.yml に移設。
- 8/17夕方の価格更新の失敗は GitHub Pages 側の一時障害（503）で、次の回で自然復旧済み。対応不要。

### 写真をどこから増やすか（2026-08-16 調査）

| 手段 | 実測 | 使えるか |
|---|---|---|
| **楽天の2枚目・3枚目** | 5件で14枚（1枚目だけなら5枚）＝**2.8倍** | **サイトで使える。実装済み** |
| 走査を深くする | 出品のあるモデル自体が増える | 実装済み |
| eBay の出品写真 | 1出品に複数枚。任意のモデルで角度が揃う | **承認待ち。本命** |
| CC画像（Openverse＝Flickr＋Wikimedia） | 型番では0件。モデル名なら数件〜24件 | 有名モデルのみ |
| Amazon アソシエイト PA-API | 商品画像の利用が明示的に許諾されている | 要審査＋180日で3件の売上 |
| メーカー公式・Chrono24 | — | **不可**（著作権・規約） |
| AI生成 | — | **不可**（実在しない個体を売り物の隣に置くことになる） |

**楽天の写真は Instagram に使えない**（規約 第10条）。サイトとInstagramで使える写真源が違うことを常に意識すること。

CC画像は Openverse の API（鍵不要だが回数制限あり）で引ける。
型番（`126610LN` など）では引けず、モデル名（`Omega Speedmaster Professional`）で引く。
実際にスピードマスターでは 裏蓋・クラスプ・真横・ムーブメント が揃った。
網羅率を正確に測るには無料の API キーが要る（無鍵だと数十回で制限に当たる）。

### Instagram を「1本の時計＋角度違いの拡大写真」にする（段階1を実装・2026-08-16）

最終目標は、1投稿＝1本の時計のロマンを綴り、その時計を様々な角度の拡大写真で見せること。
**文章側はすでにできている**（記事生成が1本＝1モデルの構成）。足りないのは写真だけ。

| 段階 | 写真源 | 状態 |
|---|---|---|
| 1 | CC / PD 画像（Wikimedia + Openverse） | **実装済み。カルーセル投稿が通しで動く** |
| 2 | eBay の出品写真 | **承認待ち。本命**（任意のモデルで角度が揃う） |
| 3 | 実機撮影 | 未着手 |

- `scripts/fetch-watch-photos.mjs` が毎朝12モデルずつ写真を集める（30日は同じモデルを調べ直さない）。
- `scripts/build-instagram-post.mjs` が2枚目以降に実写を並べる。切り抜かず余白を足す（構図を変えない）。
- `scripts/post-to-instagram.mjs` がカルーセル（子→親→公開の3段階）で投稿する。
- **写真が1枚も無い日は従来どおり1枚で出る。** 投稿が止まることはない。
- 作者・ライセンス・出典は本文に必ず出す。型番一致でない写真は「同型の別個体」と明記する。
- Openverse は鍵が無くても動くが、続けて叩くと Cloudflare のボット判定に当たる。
  鍵は `https://api.openverse.org/v1/auth_tokens/register/` に名前・説明・メールを送るだけ（無料）。
  取れたら Secrets の `OPENVERSE_CLIENT_ID` / `OPENVERSE_CLIENT_SECRET` に入れる。

### 未登録の Secrets（実害が出ている・2026-08-16 判明）

| 名前 | 影響 | 取りに行く場所 |

| `ANTHROPIC_API_KEY` | ブログが型にはめただけのものになる | **課金しない方針。下書き置き場で代替した（下記）** |
| `VC_SID` / `VC_PID` | Yahoo!の16,194出品に成果計上が付かない | **そもそも未加入**。下記参照 |

代わりに `data/blog-drafts/` に書き溜めた下書きを毎朝1本ずつ公開する。
実行ログに残り本数が出るので、少なくなったら書き足す。

テンプレートの見分け方は題名が「〜の魅力と最安値の探し方」で終わること。

**バリューコマースは使わない。** もしもアフィリエイトが Yahoo!ショッピングを扱っており、
2026-08-17に提携済み（審査なし）。**成果1.54%** でバリューコマース（約1%）より高い。

### Yahoo!（もしも経由）の規約で守ること

- **SNS・YouTube への掲載はNG。** Yahoo!の画像とリンクを Instagram に載せてはいけない。
  （楽天も規約第10条で不可。**Instagramに載せてよい商品写真は eBay 経由だけ**）
- 画像は **`store.shopping.yahoo.co.jp` の各ストアページの商品写真のみ**使える。
  検索ページ・特集ページ・PayPayモール・ストアロゴの画像は不可。
  当サイトが集めているのはストアページの商品写真なので問題ない。
- 本人申込NG。自分で買っても成果にならない。
- 再訪問90日。クリック後24時間以内にカートへ入れ、89日以内の購入完了で成果。
- 検索連動型広告・ディスプレイ広告・SNS広告への出稿はNG。

**語を足し引きしたら必ず `node scripts/test-junk.mjs` を通すこと。** 実データ100件の回帰テスト。
CI でも掃除の前に走り、落ちたらそこで止まる。

### ブランド名が別の語に埋まる問題（2026-08-17に対処）

日本語には単語の区切りが無いので、短いブランド名は別の語の一部として一致する。
**ジンの棚1,370件のうち958件（7割）が実はロンジンだった。**
ソーラーパネルの「ジンコ(JinKO)」、レーザー墨出器の「ジンバル」も入っていた。

`data/brand-match.json` に載せたブランドだけ「直前がカタカナなら別の語」として扱う。
**全ブランドに掛けてはいけない。** 掛けると1,461件が落ち、うち380件が本物だった
（ザシチズン、オフィチーネパネライ、グランドセイコー、ブライトリングプレミエ…）。

| ブランド | 混入していたもの |
|---|---|
| ジン | ロンジンの時計958件、太陽光パネル「ジンコ」、墨出器「ジンバル」、「メモリジン」 |
| ゼニス | ファルケンのサマータイヤ「アゼニス(AZENIS)」112件 |
| ラドー | 宝石「ラブラドーライト」、ピアジェ「エンペラドール」 |

2文字の「ジン」だけ `alsoAfter: true` で直後のカタカナも見る。
長い名前に掛けると「オメガスピードマスター」のような本物を落とす。

### ブランド別の「時計ではない型番」（`data/junk-refs.json`）

ベルトには本体と別の品番体系があり、商品名では見分けられない。
ハミルトンは **時計 = H+8桁 / ベルト = H605・H690・H695 + 6桁** の違いしかない。
追加するときは必ず `data/brands/<brand>.json` の人手カタログで誤爆しないことを確かめること。

### 中古店の管理番号を見分ける（2026-08-17に対処）

店は自分が扱う**全ブランドに同じ体系の番号**を振る。本物の型番は1ブランドにしか出ない。
この「散らばり」を数えて洗い出した。

| 形 | 散らばり | 例 |
|---|---|---|
| ABC+5桁 | 25ブランド 331件 | breguet/ABC18156 |
| HK+5桁 / DH+5桁 / JS+4桁 | 各19ブランド | blancpain/JS1992 |
| 先頭0の数字 | 全ブランド 237件 | rolex/0565620（本物は同じ出品の 6694） |

`isManagementRef()` で判定する。**人手カタログ968件で1件も一致しない**ことを確認済み。

あわせて「Ref.」の接頭辞796件を落とした（`REF.26393ST.OO` → `26393ST.OO`）。
接頭辞が付いたままだと、正しい型番で検索されたときに見つけてもらえない。

### 出品タイトルは自分の商品名を先に書く（2026-08-17に対処）

後ろに出る他社名は、文字盤の様式（ブレゲ数字）・愛称（ベビーパネライ）・店の扱い品目である。
**先に**他社名が出るなら、それがその商品の正体。`otherBrandComesFirst()`。

- 「セイコーSEIKO 腕時計 SUR829P1」がロレックスの棚にあった
- 「カルティエ ラドーニャSM」がラドーの棚にあった（ラドーニャ ⊃ ラドー）
- 「TISSOT ティー コンプリカシオン」がカシオの棚にあった（コンプリカシオン ⊃ カシオ）

判定には必ず `brandNameStandsAlone` を通すこと。通さないと「オリ**ジン**」の中の
「ジン」を拾って本物のG-SHOCKを消す。`SAME_FAMILY` に `orient`/`seiko` を入れてあるのは
セイコーエプソンがオリエントの親会社だから（「SEIKO EPSON … ORIENT STAR」は本物）。

### 英字の略称は他社の品番に埋まる（2026-08-17に対処）

「IWC」のような2〜4文字の英字ブランド名は、他社の品番の一部として一致する。

- アイリスオーヤマのワインセラー **IWC**-C321A-B
- レノボのノートパソコン 16**IWC**11（IdeaPad Slim 3i）

`brandNameStandsAlone` で、**前後が英数字か、直後がハイフン＋英数字なら品番の一部**とみなす。
IWCの出品1,370件のうち落ちたのは該当9件だけで、本物1,361件は残った。
この判定は `data/brand-match.json` に載っていないブランドにも効かせる（先に見る）。

あわせて家電・楽器の語を追加した（カシオの棚に同社の電子ピアノが15件あった）。

### 在庫切れの出品を載せない（2026-08-17に対処）

楽天は `availability`（1=在庫あり）、Yahoo!は `inStock`（真偽値）を返すが、
**どちらも捨てていた**。収集時に弾くようにした（`build-auto-catalog` と `fetch-prices` の両方）。

ただしデータは1日1回の収集なので、**その日のうちに売り切れる分は防げない**。
静的サイトである以上ここは避けられない。気になるなら収集を1日2回に増やすのが手。

### 海外の部品商の出品（2026-08-17に対処）

「【送料無料】腕時計　」＋ローマ字という決まった形の出品が798件ある
（ラドー236・ティソ198・ロンジン156）。**この出品者は時計も部品も両方売っている**ので、
まとめて落とせない。

| | 例 | 価格 |
|---|---|---|
| 本体 | rado womens quartz watch r20785152 | ¥294,980 |
| 部品 | tissot part no 401 for calibre 7091 winding stem | ¥16,980 |

語を二段に分けた。**確実**（part / stem / end link / mainspring）と
**文脈しだい**（movement / caliber。本体を指す語が同居していれば残す）。

欧語の部品名（cassa＝伊ケース、cadran＝仏文字盤、vetro＝伊風防）は**語順**で判定する。
部品の出品は売り物を先に書くため。ブランドの先出し判定と同じ考え方。

### 走査時間の上限（ブランドを増やしたら必ず確認する）

1ブランドあたり **2.3分**（実測89分/39社）。ブランドを増やすと走査時間が比例して伸びる。
上限に当たると**アルファベット順で後ろのブランドが毎日落ち続ける**（tissot〜zenith）。

    見積り = ブランド数 × 2.3分 + 価格100分 + 生成9分 + その他4分 < 360分（6時間）

2026-08-17に67社へ増やしたので、上限を150分→185分に引き上げた（余裕62分）。
**80社を超えるなら、価格収集の枠を削るか走査の深さ（--pages / --max-keywords）を下げること。**

### 品質面で残っている課題
- [ ] ムーブメント単体の出品が一部残る（ゼニス ¥16,980「zenith calibre 1338」など）。

## 8. 過去に踏んだ地雷（同じ失敗を繰り返さないために）

1. **`cancel-in-progress: true`** … 価格収集を3回打ち切り、写真が2日間消えた。
2. **価格の無いビルドを公開** … 中身の無いサイトが良い版を上書きした。→ 関門を追加済み。
3. **ベルトが本体として最安値になる** … 下限を出品自体の中央値から計算していたため、
   ベルトばかりの型番では下限も下がって素通りしていた。→ `data/brand-min-price.json` を併用。
4. **ブルガリ ソロテンポを消しかけた** … `ST29S` をムーブメント記号と誤判定。
   シーガルの `ST1901` はST+4桁、ブルガリはST+2桁+英字。桁数で区別する。
5. **価格でモデルごと消そうとした** … 2,354件が対象になり、中に本物の型番が含まれていた。
   安いのは出品がベルトだからで、型番自体は実在する。**消すのはモデルではなく出品**。
6. **cronだけ変えて条件式を放置** … 夕方にも記事生成とInstagram投稿が走るところだった。
7. **正規表現の記号を外し忘れ** … `A. Lange` の `.` が任意の1文字として働き、
   19世紀の医学書のPDFを大量に拾った。
8. **Wikimediaの画像をファイル名だけで判定** … 店舗の建物・コンセプトカー・偽造品を拾った。
   → Commonsの**カテゴリ**で「時計である」ことを確かめる。
9. **優先順位をブランドの中だけで上げた** … 外側のブランドの並びが変わらないので
   後ろのブランドは丸ごと時間切れで飛ぶ。優先はブランドをまたいで効かせること。
10. **投稿が失敗しても緑だった** … ステップに `continue-on-error` が付き、さらに
    リトライのループが `echo` で終わるため終了状態が常に0だった。二重に隠れていた。
    → どちらも外し、失敗したら赤くする。**握りつぶす指定は、握りつぶしてよい理由を書けるときだけ使う。**
11. **記事生成は日本時間、Instagramの2本はUTCだった** … 朝6:20はUTCではまだ前日。
    その日作った記事ではなく前日の記事を投稿しようとしていた。日付は日本時間に統一する。
12. **投稿画像がサイトに出ていないのに投稿しようとした** … Instagramは公開URLから
    画像を取得するため404だと必ず失敗する。push実行は価格データが無く公開されないので、
    push実行で作った画像はサイトに出ない。朝の定期実行なら
    画像作成→公開→投稿が同じ実行の中で順に進むので起きない。
13. **ヘッダーが幅に収まらず全ページで横スクロール** … 2回起こしている。
    1回目はナビを2段目に折り返して収めたが、その2段目の中で今度は約55pxはみ出していた。
    `space-between` は余白が無ければ配りようがなく、間隔が0まで潰れて字が隣とくっつく。
    → スマホでは項目名を短くして幅そのものを詰め、`gap` で最低幅を保証する。
    → `body` に `overflow-x: clip` を置いた（`hidden` だと `sticky` が効かなくなる）。
    これは最後の砦であって、はみ出す原因そのものは必ず直すこと。
14. **申し送り書の追記が空振りしていた** … 文字列置換で追記していたが、
    対象が一致せず何も起きないまま「更新しました」と報告していた。
    → 追記したら `grep` で入ったことを必ず確かめる。

### Actions の失敗理由を手元から読む（gh が無くても）

この PC には gh CLI が入っておらず、ログ取得の API は管理者トークンを要求する。
だが `::error::` / `::warning::` の内容（アノテーション）は**認証なしの公開APIで読める**:

1. `https://api.github.com/repos/watch-price-navi/watch-price-navi/actions/runs?per_page=30` で run を探す
2. `…/actions/runs/<run_id>/jobs` でジョブIDを取る
3. `https://api.github.com/repos/watch-price-navi/watch-price-navi/check-runs/<job_id>/annotations` に失敗理由が入っている

スクリプトの失敗メッセージを `::error::` で出す設計は、この読み出しのためにも効いている。
**失敗の理由は必ず `::error::` に書くこと**（ログ本文にしか無い情報は手元から読めない）。
